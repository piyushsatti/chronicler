# Schema design — why

Decisions baked into `0001_init.sql`. Prefer this over reconstructing intent from column lists.

## Dual-key

| Layer           | Identifier                                                | Notes                                                                                                                         |
| --------------- | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Storage / joins | `id` (`BIGINT GENERATED BY DEFAULT AS IDENTITY`)          | Every FK targets this. Compact indexes, stable for composite FKs (e.g. `pointcrawl_edges` → `pointcrawl_nodes (map_id, id)`). |
| API / URLs      | `public_id` (`UUID`, unique, default `gen_random_uuid()`) | Only value GraphQL/REST accept or emit for addressable rows.                                                                  |

**API never sees bigint.** Resolvers and HTTP handlers resolve `public_id` → internal `id` at the repository boundary, then join on bigint. Clients cannot guess or enumerate sequential ids.

Junction / ownership children use bigint FKs only. They get `id` / `public_id` only when independently addressable — see [patterns.md](patterns.md).

## Greenfield goose

Postgres starts fresh for the Go port. There is **no production Alembic history** to carry forward ([D42](../../docs/decisions/D42-Worker-And-Migrations.md)).

- One numbered SQL migration owns the initial schema (`0001_init.sql`).
- Later changes: new goose files; prefer one aggregate root per change where practical (aligns with [D26](../../docs/decisions/D26-Ten-Roots-Not-Forty-Five-Repos.md)).
- Conventions in the migration header are normative; this folder explains _why_.

## TEXT + CHECK vs Postgres ENUM

Closed vocabularies are `TEXT` (or `TEXT[]`) plus `CHECK` / array containment — not `CREATE TYPE … AS ENUM`.

| Approach      | Why chosen / rejected                                                                                                  |
| ------------- | ---------------------------------------------------------------------------------------------------------------------- |
| TEXT + CHECK  | Labels can evolve with ordinary DDL (`DROP`/`ADD` constraint). Matches vocab in `apps/api/docs/schema-v2.md`.          |
| Postgres ENUM | `ALTER TYPE` is awkward (add-only, rename friction, dump/restore quirks). Rejected for product labels that still move. |

Examples: `members.status`, `quests.kinds`, `unlockables.kind`.

## Spatial: pointcrawl-only (C3), PostGIS deferred

**Locked (2026-10-18):** [owner-decisions](../../../docs/audits/owner-decisions.md) **C3** — squashed product schema is **pointcrawl-only** (`pointcrawl_nodes`, `pointcrawl_edges`, `pointcrawl_entry_links` on `maps`; `maps.map_kind` is `pointcrawl` only). Axial hex tables and `quest_hexes` are absent from **A1** `0001_init.sql`.

PostGIS is **not** in the product model:

- Gameplay uses discrete graph nodes/edges and typed entry links, not continuous geography.
- Same-map integrity uses composite FKs on `(map_id, node_id)`, not geometry predicates.
- Revisit PostGIS only if continuous geo queries become a product requirement.

Quest ↔ map placement uses pointcrawl association (**N5**), not hex roles.

## Constraints and indexes (design posture)

- **CHECKs** encode lifecycle invariants where cheap (e.g. `quests.filled_count ≤ slots_max`).
- **Partial unique indexes** for “one open row” rules (e.g. one live `dm_table` community document per member).
- **Secondary indexes** follow hot read paths (member unread notifications, job claim by lane/state/`next_run_at`, quest board by status/`scheduled_at`).
- **Caches vs truth:** `characters.player_xp` is a cache; append-only ledger is source of truth ([D16](../../docs/decisions/D16-Ledgers-Share-A-Shape-Not-A-Table.md)).

## Aggregate roots (code boundary)

Table count ≠ repository count. Go collapses writes behind ~10 roots ([D26](../../docs/decisions/D26-Ten-Roots-Not-Forty-Five-Repos.md)). Schema still has many tables; ownership and same-transaction pairs define roots, not “one repo per CREATE TABLE”.
