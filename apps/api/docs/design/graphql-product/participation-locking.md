# Participation and retirement locking

**Status:** accepted design. Published schema/config and comment scaffolds do not implement these contracts. Runtime enforcement remains pending the owning implementation tasks and their tests.

Governing pattern: ordered pessimistic locking with bounded optimistic plan revalidation. One whole action owns its transaction, receipt and all required effects. Lock all relevant Character rows in ascending public UUID order, then all Quest rows in ascending public UUID order. No path may acquire a Character admission lock while holding a Quest lock. Repositories never commit.

Signup has one supplied Character and one Quest. Selection has the supplied distinct characterIds: set-lock admissions in UUID order, then the Quest and participation rows. Validation uses those locked admission values; no per-character lookup loop is permitted.

Withdrawal and retirement can promote another character. QuestWithdrawalWriter.PlanOwnedCharacterWithdrawal performs an unlocked set read for the owned target and preplay quest scope (empty questIDs means every current preplay live participation). It returns the complete character/quest candidate IDs plus participation createdAt/updatedAt/status bindings. CHA04 AdmissionReader.ReadImmutableOwner performs a nonlocking ID/owner lookup; QUE06 and CHA06 compare that immutable owner with current authority before planning (missing NOT_FOUND, other owner FORBIDDEN, no candidate disclosure). Neither LockAdmission nor LockRetireCharacter runs at this stage. The command authorizes the immutable owned target before planning; internal candidate facts never become a response.

Set-lock all planned Character admissions in ascending UUID order, including every potential waitlist promotion candidate, then sorted Quest rows and their participation rows. Revalidate the candidate set, statuses, versions and FIFO ordering against locked rows. If an effect would require any Character not already locked, roll back the entire action and retry the plan. Allow at most three whole-action attempts within the command deadline; further churn returns CONFLICT with no committed effects or replay receipt. Stable command-generated history IDs are retained across rollback attempts. Do not acquire a missing Character after the Quest.

QuestWithdrawalWriter.WithdrawOwnedCharacter receives the validated plan. It releases only signed_up capacity, withdraws live preplay relationships, and promotes FIFO eligible locked candidates with same-transaction notification facts. Retirement then updates the owner Character state. Postplay attendance and all existing histories remain unchanged. A producer or persistence failure rolls back withdrawals, promotions, state, job and receipt together.

Acceptance belongs to S04 mounted mutation concurrency tests: retire030 concurrently with withdrawal/promotion involving031; reverse UUID ownership order; tied waitlist timestamps with UUID tie-break; candidate inserted between plan and locks; candidate retired between plan and locks. No deadlock, partial capacity/history/card effects or promotion of an ineligible locked candidate is accepted. Inject three consecutive plan changes and assert CONFLICT plus exact unchanged original state. Two successful actions preserve signed_up count, filled_count and capacity, and emit each required promotion fact once.

Both QUE06 owner withdrawal and CHA06 retirement bind ProductCommandRepos.Withdrawals to the same QUE04 QuestWithdrawalWriter using the current transaction. Both call PlanOwnedCharacterWithdrawal then sorted LockAdmissions then sorted Quest locks/revalidation then WithdrawOwnedCharacter; neither implements a second promotion interpreter.
