# Notification facts and recipient ownership

**Status:** accepted design. Published schema/config and comment scaffolds do not implement these contracts. Runtime enforcement remains pending the owning implementation tasks and their tests.

Pattern is transactional outbox with one typed event producer. NOT08 owns event-kind recipient selection. Aggregate owners supply immutable facts on the exact originating transaction. NOT04 persists event/recipient rows and never owns a foreign aggregate's rules. This converges on the accepted addressed-notifications contract.

`notification.ProducerRepos.Recipients` composes implicit consumer-owned interfaces. CHA04 supplies CharacterOwner by immutable owner_id. DOC04 supplies DocumentAuthor. MEM04 supplies RequestParties. QUE04 supplies QuestRecipientIDs for the exact immutable quest_changes UUID. W01 binds each to the current pgx.Tx. These providers acquire no pool connection and never commit. DOC06 computes new addressed DM mentions using the canonical scoped-body parser and current Member handle resolution, then passes the exact resolved member IDs in typed Facts. NOT08 cannot parse raw text or resolve a second mention language.

Quest commands capture the resulting eligible participation members from their locked roster and persist a deduplicated recipient UUID snapshot in quest_changes together with the original old/new fact. QUE04's reader validates quest/history correspondence and returns that snapshot. It cannot query today's roster to reconstruct an earlier event. Closure after final attendance has an empty eligible set; it writes no speculative reward notification. Replayed history uses the same snapshot. Missing or malformed required originating facts fail the command and roll back. On a historical inbox read, missing proof follows HISTORY-1/ROWS-1 opaque failure and retains unread rows.

NOT08 deduplicates addressed IDs, applies only the event's actor rule, then inserts the event and required in-app recipient rows. Preferences affect channels and cannot discard required rows. Unknown event kinds fail. Event key and recipient uniqueness prevent duplicates. Event IDs, verification/revision/change/decision IDs, notification rows, business writes, desired jobs and replay receipt commit together. Any insert or recipient dependency failure rolls back the whole command.

## Bounded inbox commands and immutable proof

Pattern is CQRS with transaction-bound repositories and the canonical Document Specification. This converges on one audience owner and one command transaction.

NOT06 supplies the freshly resolved actor UUID explicitly to the ACK lock. The lock considers at most the normalized limit of100 oldest unread raw rows ordered by created_at and public UUID. It locks that selected set in public UUID order and rechecks recipient/unread state after waits. It does not refill or skip locked rows. Mark-read uses one MATERIALIZED UUID-ordered row-lock CTE and conditional UPDATE. Both paths preserve an existing read_at and return actual affected rows.

ACK validates the entire locked batch before any update. Its write carries ActorID, the locked actor-scoped candidates, one command time and SelectedIDs. Every selected ID must belong to that batch, and Locked.ActorID must match ActorID. Unknown or foreign IDs never become effects. Current hidden/missing Document subjects alone are suppressible after historical proof succeeds. Missing non-Document subjects, malformed facts, missing source history and dependency failures cause opaque failure and rollback.

SubjectKey includes NotificationID, EventID, SubjectType and SubjectID. NOT05, NOT06 and G02 retain all four identities, so two events about one entity cannot share proof or cache state. One bounded factual set query validates the addressed row/event correspondence and returns exact verification, revision, Quest change or request decision evidence, including origin actor/time and immutable recipient snapshots. Go performs exhaustive semantic matching. Copied event JSON is never independent proof. Current non-Document existence is checked in that same query. Document admission remains the canonical DOC04 set reader. W01 binds Batch, DocumentAudience, Notification, Authority and Replay to the same pgx.Tx.

Storage retains the nested discriminants in migrations.md. Facts.Version=1 is the semantic decoder version, not a new stored top-level key. The row kind selects exactly one nested discriminant. Unknown, duplicate, trailing, malformed or wrong-kind fields fail strict decoding. Each allowed field has its exact declared type; required IDs and verdict/status values cannot be null or omitted. JSONB canonicalization does not prove duplicate-input rejection, so codec boundary tests also pass raw duplicate-key bytes. Character decision keeps characterDecision.verificationId/verdict/note. Note remains optional for new events and existing stored notes retain truthful strict decoding/projection. Required request.decision comes from semantic Facts.Decision, exactly approved or declined, populated by MEM06 from its new immutable decision; accepted/requested aliases are rejected. Confirmed signup permits the accepted selection waitlisted-to-signed_up transition without rewriting prior state or relabeling it as automatic promotion. Signup and promotion add questChangeId. QUE06 supplies semantic Facts.ChangedFields from the actual immutable Quest change for the existing questChange.changedFields field. One mention event stores mention.revisionId and mention.newMentionMemberIds as a distinct resolved UUID array; there is no singular alias or per-recipient event expansion. Event kinds use subject_type character for verification, quest for signup/promotion/schedule, document for Document activity/mentions and request for request decisions. RequestID derives from the independently proved decision's immutable request FK.

DOC06 records the same resolved newMentionMemberIds set in document_revisions.new_value internal provenance before event insertion. NOT04 compares the event set to this independent revision snapshot and verifies revision/document/actor/time correspondence. Later handle changes cannot rewrite original recipients. Quest checks use quest_changes facts and recipientIds, never today's roster. Request checks use the exact request_decisions record and immutable request parties. Character checks use the exact verifications row, subject, verdict and decider/time.

Internal revision provenance is not public revision newValue or body content. DOC04/DOC05 canonical revision/history projection omits the internal newMentionMemberIds key and preserves protected-block redaction. NOT04 factual SQL may return the private snapshot for proof comparison but must never copy it wholesale into a public DTO.

Native proof remains pending real SQL generation and the shared migrations-only fixture. Required cases include opposing input orders, wait/recheck without retimestamp/refill, two events about one subject, corrupted proof beside safely suppressible rows, mixed event families, recipient confinement, unchanged cursor/budgets, and actual SQL counts at1/10/50. Existing characterDecision fixtures remain compatible. Historical expanded cases are preserved; any per-behavior compact replacement must carry added immutable proof references and exact original expectations before acceptance.
