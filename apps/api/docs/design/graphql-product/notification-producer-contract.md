# Notification facts and recipient ownership

**Status:** accepted design. Published schema/config and comment scaffolds do not implement these contracts. Runtime enforcement remains pending the owning implementation tasks and their tests.

**Superseded by owner-decisions N4 / D1 (2026-10-18):** No `notification_events` or `notification_channel_deliveries`. NOT04 persists **inbox `notifications` rows** in the same command transaction as the business write; there is no separate event ledger or delivery state table. **N3** retires `DM_REQUEST_DECIDED` and any `dm_requests` / `request_decisions` / follow-request producer seams.

Pattern is command-bound inbox generation: each row is a durable inbox fact with typed payload (normalized columns and/or JSON facts on the notification row), not a transactional outbox or event→delivery pipeline. NOT08 owns kind-specific recipient selection. Aggregate owners supply immutable proof references on the exact originating transaction. NOT04 never owns a foreign aggregate's rules. This converges on [notifications.md](/docs/interfaces/notifications.md).

`notification.ProducerRepos.Recipients` composes implicit consumer-owned interfaces on the same `pgx.Tx`. CHA04 supplies CharacterOwner by immutable `owner_id`. DOC04 supplies DocumentAuthor. QUE04 supplies QuestScheduleRecipientSnapshot for quest lifecycle kinds (immutable participant member IDs captured in the command transaction, not read from aggregate `*_changes` tables — **N2**). W01 binds each provider; they never commit. DOC06 computes new addressed DM mentions using the canonical scoped-body parser and current Member handle resolution, then passes the exact resolved member IDs in typed Facts. NOT08 cannot parse raw text or resolve a second mention language. **No MEM04 RequestParties** — request/decision kinds are retired (**N3**).

## Supported kinds (inbox-only)

| Kind                                | Proof required (same UOW)                                                                                    | Addressed members                   | Acting member                                              |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------- | ---------------------------------------------------------- |
| CHARACTER_VERIFICATION_DECIDED      | Verification row ID, Character ID, verdict                                                                   | Character owner                     | Retained if owner acts under admitted assessment authority |
| QUEST_SIGNUP_CONFIRMED              | Quest ID, Character ID, participation transition                                                             | Signing character's member          | Retained; signup is self-service                           |
| QUEST_WAITLIST_PROMOTED             | Quest ID, promoted Character ID                                                                              | Promoted character's member         | Withdrawing actor is not substituted                       |
| DOCUMENT_EDITED, DOCUMENT_PUBLISHED | Document revision ID                                                                                         | Document author                     | Excluded                                                   |
| DM_MENTIONED                        | Revision ID, resolved new-mention member IDs                                                                 | Every newly named resolvable Member | Excluded                                                   |
| QUEST_SCHEDULED                     | Quest ID, schedule/lifecycle fact + **immutable** signed_up/waitlisted member ID snapshot written in command | Snapshot members                    | Excluded                                                   |

Quest schedule/signup/promotion commands capture eligible participation members from the locked roster in the **same transaction** and persist that deduplicated UUID snapshot on the notification row facts (or equivalent normalized columns). Historical reads validate inbox facts against independent proof readers (verification row, document revision, quest row + participant snapshot stored on the notification), never today's roster and never dropped `quest_changes` history (**N2**). Closure after final attendance with an empty eligible set writes no speculative reward notification. Missing or malformed required proof fails the command and rolls back. On historical inbox read, missing proof follows HISTORY-1/ROWS-1 opaque failure and retains unread rows.

NOT08 deduplicates addressed IDs, applies only the event's actor rule, then inserts **notification rows** only. Preferences affect channels and cannot discard required in-app rows. Unknown kinds fail. `(kind, dedupe_key, recipient_id)` or equivalent uniqueness prevents duplicates. Notification IDs, verification/revision/quest proof references, business writes, desired jobs, and replay receipt commit together. Any insert or recipient dependency failure rolls back the whole command. There is **no EventID**, **no event insert**, and **no channel delivery ledger**.

NOT-PRODUCER-EXACT remains owned by NOT08 companions and S04 with the same behavioral scenarios, adapted to **one inbox row per recipient** and proof keyed by revision/verification/quest facts rather than event ledger IDs. Request-decision scenarios are **retired (N3)**.

## Bounded inbox commands and immutable proof

Pattern is CQRS with transaction-bound repositories and the canonical Document Specification.

NOT06 supplies the freshly resolved actor UUID explicitly to the ACK lock. The lock considers at most the normalized limit of 100 oldest unread raw rows ordered by `created_at` and public UUID. Mark-read uses one MATERIALIZED UUID-ordered row-lock CTE and conditional UPDATE. Both paths preserve an existing `read_at` and return actual affected rows.

ACK validates the entire locked batch before any update. Unknown or foreign IDs never become effects. Current hidden/missing Document subjects alone are suppressible after historical proof succeeds. Missing non-Document subjects, malformed facts, missing source proof, and dependency failures cause opaque failure and rollback.

**SubjectKey** for proof caching includes `NotificationID`, `SubjectType`, and `SubjectID` (no separate EventID — **N4**). NOT05, NOT06, and G02 retain notification and subject identities so two notifications about one entity cannot share proof state. One bounded factual set query validates the addressed row and returns exact verification, revision, or quest participant evidence, including origin actor/time and immutable recipient snapshots where applicable. Go performs exhaustive semantic matching. Copied JSON on the notification row is not independent proof without the paired reader check. Document admission remains the canonical DOC04 set reader. W01 binds Batch, DocumentAudience, Notification, Authority, and Replay to the same `pgx.Tx`.

Facts use a versioned nested discriminant on the notification row (`Facts.Version=1` is the semantic decoder version). Strict decoding rejects unknown, duplicate, trailing, or wrong-kind fields. Character decision keeps `verificationId` / `verdict` / optional `note`. Signup and promotion reference quest and character IDs plus changed participation fields supplied by QUE06 from the **command transaction**, not from `quest_changes`. Mention events store `revisionId` and `newMentionMemberIds` as a distinct resolved UUID array. **No request/decision discriminant** — **N3**.

DOC06 records the same resolved `newMentionMemberIds` set in `document_revisions` internal provenance before notification insertion. NOT04 compares the mention set to this independent revision snapshot and verifies revision/document/actor/time correspondence. Quest checks use the participant snapshot and schedule facts stored on the notification row plus live quest/participant proof readers, never `quest_changes` or today's roster. Character checks use the exact verifications row, subject, verdict, and decider/time.

Internal revision provenance is not public revision `newValue` or body content. DOC04/DOC05 canonical revision/history projection omits the internal `newMentionMemberIds` key and preserves protected-block redaction. NOT04 factual SQL may return the private snapshot for proof comparison but must never copy it wholesale into a public DTO.

Native proof remains pending real SQL generation and the shared migrations-only fixture. Required cases include opposing input orders, wait/recheck without retimestamp/refill, two notifications about one subject, corrupted proof beside safely suppressible rows, mixed families, recipient confinement, unchanged cursor/budgets, and actual SQL counts at 1/10/50. Historical expanded cases are preserved; any per-behavior compact replacement must carry added immutable proof references and exact original expectations before acceptance.
