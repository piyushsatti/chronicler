# DM profile review revisions

**Status:** accepted design, reconciled with owner decision N2. The retained full-replacement, revision, authority, assessment and transaction behavior is implemented in Member commands and covered by native PostgreSQL tests through the app binding.

Pattern is a transactional current projection with immutable verdict assessments and persisted command receipts. [Owner decision N2](/docs/audits/owner-decisions.md) removes non-Document aggregate history and review-event tables, including `dm_profile_review_events`. It does not change the retained field-replacement or revision rules. An earlier no-increment proposal was superseded by the stale moderator-decision race on2026-10-16.

`dm_profiles` owns the literal current fields, status and `review_revision`. `verifications` owns immutable DM-profile verdicts with the real actor, time, note and assessment UUID. Its `review_revision` stores the exact pending revision decided, while the current profile receives the next revision. There is no review-event table, workflow snapshot stream or invented notification kind.

New profile creation starts draft revision1. Every later EDIT, SUBMIT or DECIDE locks the row, compares `expectedRevision` where supplied and advances the current revision in the same transaction. Existing literal profile values and assessments are preserved; no BASELINE record or earlier actor, time, verdict or sequence is reconstructed. No repository commits.

EDIT full-replaces optional fields: omitted/null clears and supplied values replace. It requires `acceptingPlayers`, increments revision and sets draft, invalidating a pending assessment. SUBMIT from draft/rejected increments revision and sets pending. DECIDE from pending with exact `expectedRevision` records the immutable verdict, increments current revision and sets approved/rejected. A repeated pending submit with a new key is CONFLICT. An unchanged completed command with its original key replays the same result/receipt after current authority admission. Only staff with declared assessment authority may decide.

For a literal approved revision3, EDIT returns4 draft, SUBMIT(expected4) returns5 pending, DECIDE(expected5) returns6 rejected and records assessment revision5, then SUBMIT(expected6) returns7 pending. An old DECIDE(expected5) is CONFLICT at7. EDIT while pending returns8 draft and makes DECIDE(expected7) conflict. These are transition examples, not a persisted history projection. Every failure after current-row, assessment or receipt writes rolls all of them back. Reads project literal current values and immutable assessments and never repair them.
