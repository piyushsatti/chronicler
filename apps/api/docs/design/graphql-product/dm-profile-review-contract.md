# DM profile review revisions

**Status:** accepted design. Published schema/config and comment scaffolds do not implement these contracts. Runtime enforcement remains pending the owning implementation tasks and their tests.

Pattern is an append-only workflow event history with a transactional current projection. This is the schema-v2.md104-105 design, not reconstruction from a current mutable profile. Root's earlier no-increment proposal was superseded by the stale moderator-decision race on2026-10-16.

P04 adds dm_profile_review_events. It has id bigint identity PK, public_id UUID unique not null, member_id FK not null, revision int not null, kind text not null, snapshot JSONB not null, recorded_by nullable FK, recorded_at nullable timestamptz, verification_id nullable FK, UNIQUE(member_id,revision). Kinds are BASELINE, CREATE, EDIT, SUBMIT and DECIDE. snapshot is the exact profile fields tagline/philosophy/houseRules/tableInfo/acceptingPlayers plus status. Only admitted migration BASELINE may have null actor/time. New events require real actor/time. DECIDE links its immutable verifications row; other kinds leave verification_id null. verifications.review_revision stores the pending revision decided, while the decision event receives the next revision.

Migration admits one explicit BASELINE for each existing profile only after validating its stored revision/status and current snapshot. It preserves that literal cached row and revision without invented past verdict, actor, time or event sequence. The baseline is an admission record, not recovered provenance. New profile CREATE starts revision1. Every EDIT, SUBMIT or DECIDE locks the row, compares expectedRevision where supplied, appends revision+1 and maintains the current row on the same transaction. No repository commits.

EDIT full-replaces optional fields, requires acceptingPlayers, increments revision and sets draft, invalidating a pending assessment. SUBMIT from draft/rejected increments revision and sets pending. DECIDE from pending with exact expectedRevision records verdict, increments revision, and sets approved/rejected. A repeated pending submit with a new key is CONFLICT. An unchanged completed command with its original key replays the same event/receipt after current authority admission. Only staff with declared assessment authority may decide. There is no invented notification kind.

The exact history is approved baseline3, edit4 draft, submit(expected4)5 pending, decide(expected5)6 rejected, submit(expected6)7 pending. An old decision(expected5) is CONFLICT at7. Edit while pending creates8 draft and makes any decision(expected7) conflict. Every failure after event/verification/current-row/receipt writes rolls all of them back. MEM04 owns event persistence and correspondence, MEM06 owns state/authority/replay, P04 owns schema, S04 owns mounted end-to-end assertions. Reads project literal current/history values and never repair them.
