# Live authority, unit-of-work binding and request caches

**Status:** accepted design. Published schema/config and comment scaffolds do not implement these contracts. Runtime enforcement remains pending the owning implementation tasks and their tests.

Pattern: specification with live authority, unit of work, request-scoped memoization and singleflight. It converges on auth.Authority and owning Member queries. Singleflight protects the one authority refresh; it is not request-wide database serialization or a database session held across work. D27 per-task sessions/no-lock remains binding.

P06 owns existing member.PostgresStore fields and `NewFromDBTX(db dbgen.DBTX, configuredOwnerID string) (*member.PostgresStore,error)`. The existing pool constructor delegates with absent owner for legacy tests/retained consumers. W02 production builds it with the validated immutable owner configuration; W01 builds the same owning store with the current pgx.Tx for commands. ResolveAuthority reads current member/profile rows and uses P05 NewAuthorityWithOwner. The configured identity is compared only with resolved active member UUID; empty config never grants owner. The constructor validates canonical configuration syntax but does not run additional queries, commit or resolve a role from Claims. Only W04 boot validation checks that a configured identity resolves active; future live revocation still denies it. Claims role bits are never authority.

G04 owns RequestState and its exclusively owned companion tests. After pure request validation/costing, T01 invokes P07 ResolveGraphAuthority and creates it from the identity MemberID and admitted live authority. W05 supplies the resolver and providers; it does not run REST LiveMiddleware around GraphQL. Anonymous identity permits nil authority for public reads. A nonanonymous identity requires the matching initial live Authority; absent/mismatched authority is a construction failure, never an identity-only success fallback. T01 constructs G02 RequestLoaders with the state, installs them once before serving the request, and places the state in the graph context. Constructors never dispatch or acquire database connections. RequestState is absent outside GraphQL; retained HTTP protocols retain their Problem JSON boundary.

Each root and protected nested resolver obtains CurrentAuthority from RequestState. A clean cache returns the initial resolved value. InvalidateAuthority marks it dirty; the next CurrentAuthority performs one fresh owning Member task, replaces the whole Authority, and clears all request loaders. Parallel selected fields share that refresh through singleflight, without holding a lock around other database tasks. A failed refresh returns the exact expected failure/opaque dependency error and cannot return the old authority. No auth claims fallback exists.

Every successful mutation, including successful replay, clears all request-scoped loader caches in the actual registry before resolving its returned payload. Role changes and DM-profile edit/submit/decision additionally invalidate authority. MEM07 owns those explicit calls; each other domain07 owner owns the cache clear for its commands. G02 batch callbacks ask CurrentAuthority at dispatch time, never capture an old actor at loader construction. Settings/profile/relationship payloads therefore read fresh committed values; next-request live revocation is always protected. Rejected mutations clear no committed result into caches. An unexpected post-commit refresh failure cannot roll back an already committed command: errors stay opaque, durable receipt/effect remains, and reattempt still performs current authorization before receipt disclosure.

Config absent grants none, malformed config rejected at boot, configured missing/inactive member boot fails, active configured identity resolves owner only while live active. The actual production UUID is later configuration, never a test-derived deployment change.

## Flat capability decisions for DM profile workflow

The root recovered the historical ROLE_PERMS mapping from original evidence and reconciled only its still-required capabilities with CommunityR2 and current live-authority. Historical source is discovery evidence, not a token-role authorization fallback. The run's dispositions.md records the source. Roles remain flat and additive.

Self DM profile edit and submit require a currently held dm or admin capability, with configured active platform-owner bypass only as declared by D29. Approval is not required for self authoring or submit; requiring approval would make onboarding impossible. A player-only or verifier-only actor cannot edit/submit their own DM profile. Availability editing requires player or admin capability with the declared owner bypass, independently of DM capability. Staff decisions and pending-review queue require current verifier or admin capability with declared configured-owner bypass. DM alone cannot decide. No new separation-of-duty prohibition exists; a current verifier who is also the subject may decide under the same exact pending revision rule. These capabilities never grant player-character writes to a nonowner.

CAP-DM-PROFILE is owned by P02 companions and S04. Test a single-role active dm with draft profile and no prior approval editing/submitting successfully; player-only and verifier-only edit/submit FORBIDDEN. Test a single-role verifier deciding pending profile at exact revision, including its own profile, successfully; dm-only and player-only FORBIDDEN. Test admin-only for all admitted profile workflow operations. Enable owner009 explicitly in a separate config fixture and check declared bypass. An identity with admin in its token but only player in live rows is denied; demotion between requests revokes capability. A role list [dm,verifier] has the union, and [dm] never inherits verifier. Every denied case leaves profile/events/verifications/receipts unchanged. Decisions still require exact pending revision, so privilege cannot override stale workflow state.
