# Requirements — A member's cosmetics are recomputed on every read, and achievements are just one more rule type

System: [personalization-and-unlocks.md](/docs/systems/personalization-and-unlocks.md)

## Requirements

| # | Requirement | Because |
|---|---|---|
| R1 | Personalization's whole surface is exactly four groups: theme picker, mode toggle, effect toggle, accessibility set. Anything not in those four is not personalization. | The as-is surface carries a body-font picker and five flair slots; typefaces are now fixed (Fraunces + Geist) and flair is purged, so an open-ended cosmetic surface no longer has a scope boundary to sit inside. |
| R2 | Theme and mode are **two independent stored fields**, never one fused id: theme is one of 5 (Parchment default, Midnight, Ember, Dracula, Vegan), mode is tri-state (light / dark / **system**, default system). The rendered palette is the matrix cell, computed, never stored. | `member_settings` already stores "equipped mode/theme/font (string ids)" as separate columns and the live mechanism is separate `<html>` data-attributes, so the matrix is the native shape; fusing them would make 10 palettes into 10 opaque ids and lose the system option entirely. |
| R3 | `system` mode is a stored value, not the absence of a value. A member who has never chosen resolves through `system`, and a member who explicitly picks `system` is indistinguishable from them by design. | A null-means-system encoding cannot represent "I chose to follow the OS" versus "I have not chosen", and the tri-state toggle has to render one of three positions on first load with no round trip. |
| R4 | The effect toggle and the accessibility set (colorblind palette, reduced motion, density) persist per member on the same settings row, and each is readable before first paint. | Effects and motion are visible from the first frame (`Components-and-reuse.md` R9/R12); a preference fetched after mount produces a visible flash of the un-preferred state, the same class of defect as the blank `Suspense` fallback in `Loading-and-performance.md` R4. |
| R5 | Reduced motion is an **override, not a preference read once**: the stored member value and the OS `prefers-reduced-motion` signal both suppress motion, and neither can re-enable it against the other. | `Components-and-reuse.md` R12 collapses the expressive preset to `subtle-ambient` values under reduced motion; if the stored preference could override the OS signal the accessibility guarantee stops being a guarantee. |
| R6 | The purge is total and includes **earned** unlocks: every pixel-era theme, the Pixel/Retro font category, and all five flair slots leave the catalog, the ledger, and the settings row. No cosmetic survives because someone earned it. | As-is verdict 2: grants are recomputed on every read against the current rule set, so a retired catalog row is not merely unused, it keeps being re-evaluated; leaving purged cosmetics in `unlockables` means `reconcile_unlocks` continues granting them. |
| R7 | The catalog/ledger/reconcile machinery **survives the purge** and is retained for achievements and DM tiers, which are not cosmetics. Personalization stops being a consumer of the ledger. | As-is verdict 4: achievements and DM tiers are already `unlockRule` types in the same catalog, admin-grant-only; deleting the machinery with the cosmetics would take a live non-cosmetic system with it. |
| R8 | Every theme × mode cell is validated against the contrast floors (WCAG AA, plus the not-too-dark-ground rule C13) before it is selectable, and a cell that fails is not shippable. | 10 palettes shipping at launch is 10 independent chances to ship an unreadable surface; the as-is system has no validation on theme data at all (`upsertUnlockable` accepts raw JSON, assumption A1). |
